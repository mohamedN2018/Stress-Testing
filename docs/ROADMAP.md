# خطة تطوير وتحديث Sentinel Test Lab

**هذه وثيقة تخطيط — البنود المشطوبة فقط نُفّذت، والباقي لم يُنفَّذ.** كُتبت ليستطيع أي مطوّر تنفيذها لاحقاً بالترتيب الذي يناسبه.
الحالة الحالية للتطبيق موثّقة في `CAPABILITIES.md`، وبنية الكود في `ARCHITECTURE.md`.

## 1. الهدف والمبادئ

التطبيق أداة لاختبار **مشاريعك الخاصة** قبل وبعد النشر: هل تتحمل الحمل؟ هل إعداداتها الأمنية سليمة؟ هل فيها أخطاء؟

مبادئ يجب أن يحافظ عليها أي تطوير:

1. **لا اختبار بلا تصريح**: كل ميزة جديدة تمر عبر `SafetyManager` وقائمة الأهداف المصرّح بها.
2. **دفاعي لا هجومي**: الميزة ترصد "هل الحماية موجودة وتعمل؟" ولا تحاول اختراقها أو تجاوزها.
3. **قياسات حقيقية فقط**: ما لم يُقَس يُكتب "غير متاح".
4. **حدود ثابتة**: كل ميزة ترسل طلبات لها سقف في الكود وميزانية طلبات.
5. **كل ميزة تُسلَّم مع اختبار آلي** مقابل الخادم المحلي في `tests/support/local_server.py`.

### ما يجب ألا يُضاف أبداً

توليد حمل موزّع من عدة مصادر، تدوير proxies أو تزييف المصدر، تجاوز rate limit / WAF / CAPTCHA،
قوائم كلمات مرور أو تخمينها، استغلال الثغرات أو استخراج البيانات، فحص أهداف لم يُصرَّح بها أو فحص نطاقات IP.
هذه تحوّل الأداة من اختبار إلى هجوم، وتعرّض صاحبها للمساءلة القانونية.

## 4. المرحلة 2 — اختبارات تشبه الاستخدام الحقيقي

| # | الميزة | الوصف | أين في الكود |
|---|---|---|---|
| 2.1 | سيناريوهات متعددة الخطوات | رحلة مستخدم: فتح الصفحة ← دخول بحساب اختبار ← تصفح ← إجراء. كل مستخدم افتراضي يحتفظ بجلسته وكوكيزه | محرك جديد `engines/scenario/` فوق `HttpRunner`؛ محرّر خطوات في الواجهة |

| 2.6 | نماذج حمل إضافية | Soak (حمل خفيف لمدة طويلة لكشف تسرب الذاكرة)، وحمل بمعدل ثابت (open model) | محركات صغيرة فوق `HttpRunner`؛ رفع سقف المدة للأهداف المحلية فقط |
| 2.7 | بيانات اختبار | ملف CSV بحسابات اختبار متعددة أو كلمات بحث، يوزَّع على المستخدمين الافتراضيين | قارئ بيانات + تأكيد أنها حسابات اختبار |

معيار القبول العام: سيناريو "دخول ثم 3 صفحات" يعمل على خادم الاختبار المحلي، وتظهر مقاييس كل خطوة منفصلة.

## 5. المرحلة 3 — رؤية ما يحدث داخل الخادم

حالياً التطبيق يقيس جهازك فقط. الهدف: ربط البطء بسببه.

| # | الميزة | الوصف |
|---|---|---|
| 3.1 | مقاييس Docker | قراءة `docker stats` للحاويات (محلياً أو عبر SSH): CPU/RAM لكل حاوية أثناء الاختبار |
| 3.2 | مقاييس الخادم البعيد | عبر SSH بمفتاح (قراءة فقط) أو عبر Prometheus/node_exporter إن وُجد |
| 3.3 | PostgreSQL | اتصالات نشطة، أقفال، أبطأ الاستعلامات أثناء الاختبار (`pg_stat_activity`, `pg_stat_statements`) بمستخدم قراءة فقط |
| 3.4 | Redis و Celery | الذاكرة، عدد المفاتيح، طول الطوابير، المهام المتأخرة |
| 3.5 | ربط زمني | وضع مقاييس الخادم على نفس محور الزمن مع RPS وزمن الاستجابة في الرسوم والتقرير |

ملاحظات تنفيذ: الواجهة جاهزة لذلك (بطاقة "قاعدة البيانات" تعرض "غير متاح" الآن). أضف مصادر مقاييس
تحت `monitoring/` بواجهة موحّدة `sample() -> dict` وسجّلها في sampler الـ orchestrator. بيانات الاتصال
تُحفظ في Credential Manager مثل باقي الأسرار.

## 9. تحسينات تقنية داخلية

- فصل الثوابت النصية العربية من ملفات الواجهة إلى مكان واحد (تمهيد لـ 1.8).
- تثبيت اتصالات HTTP على عناوين IP المصرّح بها (DNS pinning على مستوى الـ transport) بدل إعادة الفحص قبل التشغيل فقط.
- تخزين العيّنات الزمنية في جدول مستقل بدل JSON داخل صف التشغيل (مطلوب للاختبارات الطويلة في 2.6).
- نسخ احتياطي واستعادة لقاعدة البيانات من صفحة الإعدادات، وسياسة حذف للتشغيلات القديمة.
- قياس تغطية الاختبارات وإضافة فحص أنواع (mypy) و lint (ruff) إلى CI.
- اختبار التطبيق على شاشات عالية الدقة (HiDPI) وبمقاسات نوافذ صغيرة.

## 10. كيف تُنفَّذ أي ميزة

1. اقرأ `ARCHITECTURE.md` قسم "إضافة نوع اختبار جديد".
2. اكتب أولاً قواعد الأمان للميزة (الحد الأقصى للطلبات، هل تحتاج هدفاً موثوقاً؟) واختباراتها.
3. أضف endpoint في الخادم المحلي يمثّل الحالة السليمة والحالة المعيبة، واكتب اختبار تكامل للحالتين.
4. نفّذ المحرك، ثم الصفحة، ثم جدول التقرير.
5. حدّث `CAPABILITIES.md`: انقل الميزة إلى "مدعوم" فقط بعد تجربتها على هدف حقيقي تملكه.
